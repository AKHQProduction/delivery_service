# Address Autocomplete Design

## Goal

Добавить автокомплит адреса в двух существующих местах фронтенда:

- адреса клиента через `AddressInputList`
- адрес магазина через `ShopAddressForm`

Автокомплит должен работать через backend API проекта, а не через прямые вызовы провайдеров с фронтенда. После выбора подсказки адрес должен подтверждаться на карте. Для адресов клиента нужно автоматически подставлять район из уже созданных районов пользователя, если совпадение найдено.

## Scope

Входит в работу:

- новый backend endpoint для подсказок адреса
- общая frontend-логика автокомплита для двух существующих мест ввода
- открытие карты после выбора подсказки
- автозаполнение `district_id` у адреса клиента

Не входит в работу:

- изменения в формах заказа
- прямые вызовы HERE или Google с фронтенда
- сложный fuzzy matching районов
- отдельные frontend unit/integration tests, так как в проекте сейчас нет frontend test setup

## Existing Context

### Frontend

Адрес клиента редактируется через общий компонент `frontend/src/components/shared/AddressInputList.tsx`, который используется в:

- `frontend/src/components/forms/client/AddClientForm.tsx`
- `frontend/src/components/forms/client/EditClientForm.tsx`

Адрес магазина редактируется в:

- `frontend/src/components/settings/ShopAddressForm.tsx`

Сейчас фронтенд уже умеет:

- делать `forward geocode` и `reverse geocode` через backend
- открывать карту для ручного подтверждения адреса
- сбрасывать координаты при ручном изменении `street` или `house`

### Backend

Сейчас backend предоставляет только:

- `GET /v1/geocoding/forward`
- `GET /v1/geocoding/reverse`

Провайдеры геокодинга уже инкапсулированы на backend. Этот подход нужно сохранить и для нового флоу подсказок.

### Districts

Районы пользователя сейчас представлены только как пользовательские сущности с полем имени. Геометрии района в системе нет. Поэтому определение района возможно только по имени района, которое вернёт провайдер в `reverse geocode`, с последующим сопоставлением с существующими районами магазина.

## User-Approved Behavior

Согласованное поведение:

- автокомплит должен подсказывать `улица + дом`, а если дом ещё не введён или не найден, то хотя бы улицу
- после выбора подсказки адрес не считается окончательно подтверждённым, пока пользователь не подтвердит точку на карте
- если район удалось сопоставить с пользовательскими районами, поле района заполняется автоматически
- если совпадений по району нет, поле района остаётся пустым
- если совпадений несколько, выбирается первый найденный район
- автокомплит делается только для адресов клиента и адреса магазина

## Proposed Architecture

### Backend

Добавить новый endpoint:

- `GET /v1/geocoding/suggest`

Параметры:

- `query: str` — текст, введённый пользователем
- `city: str` — город, в контексте которого ищем адрес
- `limit: int | None` — опциональный лимит результата

Ответ:

- список подсказок в нормализованном формате

Предлагаемый формат одного элемента:

- `label: str` — строка для отображения в dropdown
- `street: str`
- `house: str`
- `city: str`
- `coordinates: { latitude: float, longitude: float } | null`

Endpoint остаётся thin controller. Основная логика живёт в application/infrastructure слое рядом с текущим geocoder abstraction. Backend сам решает, какой провайдер использовать, и скрывает детали HERE/Google от фронтенда.

### Frontend

Добавить общий переиспользуемый слой автокомплита адреса:

- сервис API для `geocoding/suggest`
- общий hook для debounce, загрузки подсказок, выбора элемента и закрытия dropdown
- UI-рендер списка подсказок под полем ввода улицы

Этот слой подключается в:

- `AddressInputList`
- `ShopAddressForm`

Логика должна быть общей, а интеграционный код для конкретной формы — минимальным.

## Detailed Flow

### Client Address Flow

1. Пользователь вводит текст в поле улицы.
2. После debounce фронтенд вызывает `GET /v1/geocoding/suggest`.
3. Под полем показывается dropdown с подсказками.
4. Подсказки с распознанным домом должны отображаться выше подсказок без дома.
5. Пользователь выбирает подсказку.
6. Форма заполняет:
   - `street`
   - `house`
   - предварительные `coordinates`, если они пришли
7. Сразу после выбора открывается карта для подтверждения точки.
8. После подтверждения на карте:
   - обновляются итоговые координаты
   - при необходимости уточняются `street`, `house`, `city` через `reverse geocode`
   - из `reverse geocode` берётся `district`
   - выполняется поиск первого района из пользовательского списка, чьё имя совпадает с нормализованным именем района из ответа
   - если совпадение найдено, записывается `district_id`
   - если совпадение не найдено, `district_id` остаётся пустым
9. Если пользователь затем вручную меняет `street` или `house`, предварительные координаты и статус подтверждения сбрасываются по текущему паттерну формы.

### Shop Address Flow

1. Пользователь вводит текст адреса.
2. После debounce фронтенд вызывает `GET /v1/geocoding/suggest`.
3. Под полем улицы показывается dropdown подсказок.
4. Пользователь выбирает подсказку.
5. Форма заполняет:
   - `street`
   - `house`
   - предварительные `coordinates`, если они пришли
6. Сразу после выбора открывается карта для подтверждения точки.
7. После подтверждения карта возвращает итоговые координаты и при необходимости уточнённый адрес через `reverse geocode`.
8. Только после подтверждения вызывается текущее сохранение адреса магазина.

## UX Rules

- Dropdown подсказок открывается только если введён непустой запрос.
- Запросы должны быть задебаунсены, чтобы не создавать лишнюю нагрузку.
- При новом вводе предыдущие подсказки и предыдущий выбор должны инвалидироваться.
- Если backend вернул пустой список, dropdown скрывается или показывает лаконичное состояние “ничего не найдено”.
- Выбор подсказки не должен сразу сохранять данные на backend.
- Карта остаётся обязательным шагом подтверждения.

## District Matching Rules

Матчинг района должен быть консервативным:

- сравнение по имени района после базовой нормализации
- минимальная нормализация: `trim`, `lowercase`
- допускается лёгкая очистка стандартных префиксов вроде `район` или `р-н`, если это понадобится для стабильности
- агрессивный fuzzy matching не нужен
- если найдено несколько совпадений, выбирается первый
- если совпадений нет, `district_id` остаётся пустым

## Error Handling

- Если `suggest` временно недоступен, форма должна продолжать работать как обычный ручной ввод.
- Если пользователь выбрал подсказку без координат, карта всё равно открывается, но стартует по имеющимся данным формы.
- Если `reverse geocode` после подтверждения карты не вернул район, автозаполнение района пропускается.
- Ошибки автокомплита не должны блокировать ручной ввод и ручной выбор адреса на карте.

## Testing Strategy

### Backend

Добавить backend тесты на новый endpoint и нормализацию результата:

- endpoint возвращает пустой список при отсутствии подсказок
- endpoint возвращает подсказку с домом, если провайдер нашёл дом
- endpoint возвращает подсказку только с улицей, если дом не найден
- ответ сериализуется в согласованный формат

### Frontend

Так как в проекте нет frontend test setup, проверка на фронтенде должна быть через ручной smoke/regression прогон:

- адрес клиента: ввод, показ dropdown, выбор подсказки, открытие карты, подтверждение, заполнение района
- адрес клиента: отсутствие совпадения по району оставляет поле пустым
- адрес клиента: при нескольких совпадениях по району выбирается первый
- адрес магазина: ввод, показ dropdown, выбор подсказки, подтверждение на карте, сохранение
- ручное редактирование после выбора подсказки сбрасывает предварительные координаты

## Files Likely To Change

Backend:

- `backend/src/backend/presentation/http/v1/routes/geocoding.py`
- schema/dto files для ответа списка подсказок
- application service layer рядом с текущим `Geocoder`
- provider implementations или адаптер поверх них для режима suggestions
- backend tests for geocoding route/service

Frontend:

- `frontend/src/services/api/geocodingApi.ts`
- новый shared hook/component для autocomplete
- `frontend/src/components/shared/AddressInputList.tsx`
- `frontend/src/components/settings/ShopAddressForm.tsx`

## Rollout Notes

- Новая функциональность должна быть обратно совместима с текущим ручным вводом.
- Если suggestions ведут себя нестабильно у конкретного провайдера, фронтенд не должен ломаться.
- Реализация должна быть сосредоточена на этих двух существующих точках ввода без расширения scope.
